# Windows VS Code 本机验收

本文件中的所有真实宿主检查均为 **待执行**。执行本文件会在用户已登录的 Codex 环境中调用模型，并可能产生用量。先使用测试仓库与只读子会话。

## 1. 固定宿主和接口

记录以下信息，不上传认证文件或 API 密钥：

| 项目 | 本机记录 |
| --- | --- |
| Windows / VS Code 版本 | 待填写 |
| Codex 扩展版本及安装路径 | 待填写 |
| 执行 CLI 路径和 `--version` | 待填写 |
| queue CLI 路径和 `--version` | 待填写 |
| 原主线程 UUID 与确认方式 | 待填写 |
| 原主线程模型 | 待填写 |
| 子模型、provider key、effort | 待填写 |
| IDE、CLI 是否同机、同用户、同 CODEX_HOME | 待填写 |
| `doctor` 三项能力检查 | 待填写 |

`doctor.json` 位于工具 state 目录。不要用安装了 `queue` 的另一台机器来替代当前 IDE 宿主测试。

## 2. 单独验证原 IDE 自动执行

在原 VS Code Astra 会话确认其真实 Thread ID。可以使用宿主明确提供的当前 ID，或核对对应本地会话日志中的 `session_meta.id`。模型根据标题猜出的 ID、其他终端线程 ID、Desktop 聊天 ID 均不合格。无法可靠识别时停止发送探针，先解决身份识别。

让原 Astra 在它的 shell 中执行下面的命令，随后立即结束当前回合。命令中的路径和 UUID 必须已核实：

```powershell
python 'C:\实际路径\codex-subchats\subchats.py' `
  --state 'C:\Users\实际用户\AppData\Local\codex-subchats' `
  probe-wake --parent-thread '原IDE线程UUID' `
  --cwd 'C:\实际路径\测试仓库' --delay 20
```

`--delay` 给原回合留出结束时间。命令会立即返回探针 Run ID 和 `SUBCHATS_WAKE_...` 随机标记。**原回合必须在消息投递前自然结束；不要点 Stop，也不要手动发送标记。**

保留 VS Code 窗口和原会话，观察 60 秒（本机测试窗口，不是接口保证）。期间不要点击 Send、Resume、补发「继续」或让另一个 CLI 恢复原主线程。

结果分级：

| 观察 | 判定 |
| --- | --- |
| queue 帮助不可用或发送报错 | 本环境未通过队列能力检查 |
| `notification.status=queued`，界面没有新执行 | 仅入队，自动执行未证实 |
| 界面出现待发送消息，须手动点击 | 自动唤醒未通过 |
| 原线程自动开始新回合，助手回复完全匹配随机标记 | 本次宿主自动执行证据成立 |
| 回复出现在另一个线程 | 原线程唤醒失败 |

仅看到 queue 输出不能升级判定。建议保留带时间的原线程日志或连续屏幕记录，以区分自然结束、自动开始和人工输入。

如果存在可读取的 JSONL rollout，可用辅助命令核对助手回复：

```powershell
python .\subchats.py --state $subchatsState observe-probe 'PROBE_RUN_UUID' `
  --parent-rollout 'C:\准确路径\原线程rollout.jsonl'
```

它只核对 `session_meta.id` 与助手消息，拒绝把用户消息当作回复。报告即使显示 `assistant_reply_observed=true`，也仍保留 `automatic_execution_verified=false`：单靠落盘文本无法证明没有手动操作。若当前版本没有这种日志格式，记录「观察器不适用」，用宿主事件或人工连续观察取证，不修改 Codex 存储。

## 3. 验证真实子模型和恢复

按 README 创建只读子会话，要求固定短回复。检查：CLI 返回成功、输出符合请求、`thread.started` 和单个 `turn.completed` 都存在。随后 `send` 一次，核对恢复前后 UUID 完全一致。

配置中的模型是请求值。若使用自定义网关，结合网关日志确认实际路由；工具不会把 `--model` 参数本身当成模型身份认证。

## 4. 三轮真实闭环

安装 MCP 后，在原 Astra 会话给出一次明确授权：

```text
用 codex-subchats 完成这次三轮只读验收。
原主线程 UUID 为：<已核实的 UUID>。
子任务目录为：<独立测试仓库绝对路径>。
每轮使用新的 request_key；始终复用第1轮创建的子会话。
第1轮让子会话列出测试仓库结构；第2轮让它解释一个选定源码文件；
第3轮让它指出该文件一个值得检查的问题，没有问题可以说明。
每次派发后结束当前回合，不轮询、不使用 wait 工具保持模型回合。
只有原线程自动收到完成事件后才读取结果、复核并派发下一轮。
第3轮复核后停止，不启动第4轮。
```

这段提示由用户显式使用，不自动注入。记录：

| 轮次 | Run ID | 子 Thread ID | 入队 message_id | 原回合结束 | 自动新回合 | 复核/下一轮 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |
| 2 | 待填 | 同第1轮 | 待填 | 待填 | 待填 | 待填 |
| 3 | 待填 | 同第1轮 | 待填 | 待填 | 待填 | 复核后停止 |

必须连续三轮均无需人工唤醒，才能完成这部分 P2。单独三次 queue 成功不合格。

## 5. 有限边界验收

只补充与当前工作流直接相关的项目：

1. 子任务运行期间关闭并重新连接 MCP，确认任务没有因此重复或丢失；按原 ID 读取结果。
2. 在慢任务运行期间重复相同 request_key，确认只有一个执行；对同一 cwd 派发另一个任务，应拒绝。
3. 取消一个测试任务，确认 Codex 子进程树停止、状态为 cancelled；改动不会自动回滚。
4. 窗口重载后查看队列与原线程。分别记录「已自动消费」「重新打开原线程后消费」「需要人工输入」。不要将重载前的成功推广到重载后。
5. 切换到另一聊天后，让原线程接收一次探针，确认原线程仍能自动执行。若不能，记录已验证支持范围为「保持原聊天加载」。

传输层重复事件、发送确认丢失、状态重开恢复已有替身测试。真实断网或主机重启不要求大规模故障注入；发生后保留现场，不自动重放未知执行。

## 停止与替代

如果第2步失败，不继续把三轮人工点击记为自动验收。可继续使用独立子会话与持久化结果，用户在原 Astra 会话发送一次「读取 RUN_UUID 并继续」。收集 `doctor.json`、相关 Run 的 queue.stdout/queue.stderr、扩展版本和观察结果后，再决定是否研究同一 App Server 端点。
